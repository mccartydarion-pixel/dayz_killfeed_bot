# C.A.S.E. Gate D — guarded staff review transaction and route

The neutral queue/history reads now have a **default-off** companion POST `/anti-cheat/cases/{caseID}/review` candidate. It accepts only an opaque 64-character action key, expected status, target status, allowlisted reason code and neutral note. Actor, guild, server and installation come entirely from authenticated selected-installation context, never JSON. The route requires privileged location-view capability, a bounded strict JSON body, rate limiting and an additional scoped OWNER/ADMIN membership check inside the transaction.

**Two independent release gates:** `CHAMPION_CASE_REVIEW_WRITES_ENABLED=true` must be explicitly operator-approved, and the actual immutable detector registry must contain a `VALIDATED_SHADOW` detector. The repository further row-locks the target case, requires its exact detector ID/version to be independently validated and at least one exact linked persisted evidence row. With the current registry (only blocked CASE-MOV-001), the endpoint returns 404 even if somebody sets the environment switch. It is not case admission; the future producer must separately prove current source/evidence eligibility before writing a case.

The common transaction holds membership and case locks, serializes revocation, allows only neutral PENDING_REVIEW -> REVIEWED/DISMISSED -> RESOLVED transitions with allowlisted reasons, appends one immutable audit with the status update in the same commit and rejects action-key collisions. A matching real HTTP retry reuses the original audit/status without requiring the server-generated timestamp to be identical; the synthetic fixture method retains exact-time replay checks. It creates no new finding, outbox row, private Discord message or sanction.

The existing synthetic `ApplySynthetic` still requires both fixture flags and has no live caller. The production `ApplyReviewed` entrypoint is reachable only through the doubly gated handler; neither flag is changed by this PR. No additional poller, migration or economy code changes. These are implementation checks, **not full real-data or end-to-end acceptance**, and Gates A–G stay open. Production merge and any eventual flag activation require separate explicit owner approval.
